# /아이루

질문: $ARGUMENTS

`aimobi` MCP 도구로 서버의 최신 저장소, 운영 DB, Jira(모두 읽기 전용)를 직접 확인하며 답한다. 대화는 이 세션에서 이어 가고, 이후 질문도 같은 도구로 확인한다. 질문이 비어 있으면 무엇을 확인할지 묻는다.

## 확인하는 법

1. 저장소 고르기: 이 대화에서 이미 고른 저장소가 있으면 그대로 쓴다. 질문에 업체·시스템 이름이 분명하면 `repositories`의 목록과 설명으로 고른다. 분명하지 않거나 새 주제면 `find_repository`에 질문(업체, 화면, 메뉴, URL, 증상 등 아는 것 전부)을 넣는다. 업체 이름을 넣으면 보통 몇 초 안에 답한다. 결과가 status "running"이면 같은 job으로 다시 부르고, 기다리는 동안 "저장소를 찾는 중"이라고 한 줄만 알린다. 결과의 저장소가 여럿이면 앞의 것부터 확인하고, none이면 사용자에게 시스템을 묻는다.
   `ftp-<도메인>` 저장소는 FTP로 올리는 웹호스팅 홈페이지의 운영 사본(코드 파일만)이다. 같은 사이트의 GitHub 저장소와 내용이 다르면 ftp 쪽이 지금 운영 중인 코드다. 링크는 `ftp://<도메인>/<경로>#L<줄>`로 나오고 웹에서 열리지 않으니 경로와 줄 번호로 인용한다. `history`는 사본을 받은 시점만 보여 준다.
2. 코드는 `search`로 위치를 찾고 `read`로 끝까지 읽는다. 동작은 읽은 코드로만 말하고, 결과의 GitHub 링크(파일#줄)를 근거로 붙인다.
3. 데이터가 필요하면 업체가 있을 때 먼저 `customer`(업체 이름)로 그 업체의 DB 서버·DB를 확인하고, `db_tables` → `db_columns`로 구조를 본 뒤 `db_query`. 업체를 모를 때만 `db_servers`부터 본다. SELECT 하나, 끝에 LIMIT, 인덱스가 있는 조건(번호, 날짜 범위)으로 좁힌다.
4. 바뀐 시점이나 담당자가 필요하면 `history`, `commit`.
5. Jira 이슈 번호(ABC-123 꼴)가 나오면 `jira_issue`로 본문·댓글·연결 이슈를 읽는다. 같은 문제가 이미 올라왔는지, 이전에 어떻게 처리됐는지는 `jira_search`(text에 업체·화면·증상 단어)로 찾는다.

## 답하는 법

- 확인한 것과 추정을 나눈다. 읽지 않은 코드, 조회하지 않은 데이터로 단정하지 않는다.
- 저장소의 기본 브랜치가 운영에 배포된 코드다. 저장소 설명에 운영과 다를 수 있다고 적혀 있으면 그렇게 밝힌다.
- 도구 한 번에 몇 초씩 걸린다. 필요한 만큼만 부르고, 같은 내용을 다시 읽지 않는다.
- DB 결과의 개인정보(이름, 연락처, 면허번호 등)는 답에 꼭 필요할 때만 쓴다. 다른 곳에 옮겨 적을 때는 값 대신 위치만 쓴다.
- 도구 오류(서버 꺼짐, 토큰 오류)는 그 문장을 그대로 전하고 멈춘다.
- 코드를 고치자고 하면 로컬 저장소에서 작업한다. 서버 도구는 읽기만 한다.
